    Install and configure Enterprise¶

    This guide applies to beta9 R3. Enterprise uses PostgreSQL and central identity management. Use only the Enterprise package on Windows Server, RDP and Citrix systems.

    1. Plan topology and requirements¶

    All-in-one server: PostgreSQL, API, worker, archive service and provisioning service run on the same Windows server. A client can run in a user session there. There is no special combined runtime mode.

    Distributed installation: Clients run on separate computers; server services remain independent components. Plan reachable database endpoints and server-bound file archives. The provisioning service belongs to the trusted server context; clients receive no administrative passwords.

    Decide before starting:

    • 64-bit Windows and local administrative installation rights; size resources for customer count, archive volume and concurrency.
    • A stable HTTPS address such as https://fleet.example.internal:8443, with a matching certificate SAN. Private keys stay on the server.
    • PostgreSQL data on a local fixed NTFS volume, not a network drive or user profile.
    • Separate protected customer data/archive roots and backup destinations outside the running system.
    • Firewall access: HTTPS from clients to the API host; PostgreSQL only for authorized hosts. Do not publicly expose the database, service control or provisioning named pipe.
    • For remote PostgreSQL connections, configure TLS according to operational policy with verified certificate chain and host identity.

    2. Verify files and existing installations¶

    Download installers and checksums, compare SHA-256 and observe beta status. Before updating, stop client access and create verified database, archive, configuration and key backups. An existing customer database must never automatically become the control database.

    Existing-installation conversion is maintenance

    The server setup below creates a new platform. Existing single-customer installations require explicitly planned conversion with verified backup and rollback. A copy or matching username does not authorize identity merging.

    3. Install PostgreSQL¶

    1. Run the PostgreSQL server installer elevated.
    2. Configure local storage, port and the required database passwords. Keep passwords separately protected.
    3. The default local Windows service account is mira_postgres. A custom permitted account name must be unused for a fresh installation; existing accounts are not adopted or reset.
    4. Complete installation and check postgresql-x64-mira.

    The database and Enterprise installers are separate packages. An existing PostgreSQL service name alone does not establish a suitable empty target platform.

    4. Configure a new platform¶

    Unattended setup reads a protected INI through /MIRACONFIG. This example shows structure only, not usable credentials:

    [tenant_server]
Host=127.0.0.1
Port=5432
SetupUser=postgres
SetupPassword=<enter-locally>
AdministratorPassword=<strong-personal-password>
PublicUrl=https://fleet.example.internal:8443
Bind=0.0.0.0
Certificate=C:\FleetMiraSetup\server.pem
PrivateKey=C:\FleetMiraSetup\server-key.pem

    Do not put the INI or TLS key in Git, email or shared download folders. The setup INI must be owned by SYSTEM or the built-in Administrators group and grant access only to those identities. An additional individual administrator ACE is rejected too.

    The standalone permission routine audits without changes by default. Run elevated:

    .\protect_enterprise_setup_inputs.ps1 -LiteralPath C:\FleetMiraSetup\enterprise.ini -Mode Audit
.\protect_enterprise_setup_inputs.ps1 -LiteralPath C:\FleetMiraSetup\enterprise.ini -Mode Protect -BackupManifest C:\FleetMiraSetup\acl-before.json -RequireCompliant

    BackupManifest must be new. The routine changes permissions, not file contents; -Mode Restore with the same manifest restores saved permissions for exactly the same files. Protect the manifest itself. Protect TLS files and other setup inputs according to their actual secrets.

    5. Install Enterprise components¶

    1. Run the Enterprise installer elevated. On the server select the client if required, Fleet Mira Worker Windows service and Fleet Mira API Windows service.
    2. Supply the complete protected file for a new platform. Example:
    .\FLEET-Mira-Enterprise-1.1.0-beta9-Setup-x64.exe /TYPE=custom /COMPONENTS=client,worker,api /MIRACONFIG="C:\FleetMiraSetup\enterprise.ini"
    1. Wait for successful completion. Setup creates a separate control database and the first central administrator. Customers are provisioned explicitly afterwards.
    2. Check FleetMiraApi, FleetMiraWorker, FleetMiraArchive, FleetMiraProvisioner and PostgreSQL. API, worker and archive use their own restricted service identities. The local provisioning service runs as SYSTEM for explicitly authorized maintenance.
    3. Sign in as the first administrator using the password set in the setup file. Never reuse example passwords.

    Customer databases use protected runtime roles. Do not grant clients ownership, superuser or role-management privileges. Resolve configuration failures and retry normally; do not disable safety checks.

    6. Connect clients and activate¶

    Install only the Enterprise client on additional workstations and point its client configuration to the platform HTTPS address. Sign-in uses central identities; authorized database targets and short-lived credentials come from the server, not a user-supplied DSN.

    The public client file is named enterprise-client.json. It contains only the trusted server origin and optional public CA paths, never a DSN or database passwords:

    {"schema":1,"public_url":"https://fleet.example.internal:8443"}

    Setup supplies the profile beside the Enterprise installation. For administrative distribution, optional ca_file and pg_ca_file paths are relative to the profile; use public CA certificates only. Remote PostgreSQL targets require verify-full and matching host identity. Local prefer mode does not authorize unprotected network operation.

    Distribute private enterprise CAs through managed deployment and verify their fingerprints. Hostname, validity and SAN must match; never disable certificate verification or copy private server/CA keys to clients.

    As a platform administrator, activate the base license, then set up the first and additional tenants. Each tenant receives its own database and storage; clients do not start local background workers.

    7. Verify readiness¶

    • Check the Health page and local service console: process running, valid license, reachable database and current worker heartbeat.
    • Open each authorized tenant and verify the displayed identity and role-based access.
    • Run a harmless central job in an authorized test environment and check its actual result.
    • Configure and practically verify backup and restore.
    • Reboot the server and check automatic service startup and client access again. The worker may start with a delay; an open HTTPS port alone is not readiness.

    Errors and updates¶

    Investigate setup failures through protected installation logs. Use the local console if the API is unavailable; central licensing remains authoritative for license problems. Apply shared versioned schema maintenance administratively after updates, before clients and workers use the new version. Never force migrations through normal client roles.

    The verified R3 single-server deployment does not replace acceptance of customer-specific UNC/gMSA, network, cloud, security software or load configurations.
